## 2. 本轮浏览器复现记录

复现方式：Playwright + Chromium，登录管理员账号，进入 `/ship-tracking`，默认每页 50 条。

### 2.1 复现环境

- 1600×900：表格可视宽度 1454px，表格内容总宽 1912px，最大横向滚动 458px。
- 1366×768：表格可视宽度 1220px，表格内容总宽 1912px，最大横向滚动 692px。
- 固定列：选择列 46px + 模块 150px + 梯号 185px = 左侧 381px；右侧「操作」78px。
- 表格使用 `max-height`，50 行时纵向和横向滚动均可用。

### 2.2 关键发现

1. **数据没有丢**。以伊拉克模块为例，接口和 DOM 中都有合同号和项目名称：
   - `DHT-261493T/1#`：合同号 `DHT-261493T`，项目 `992026S`。
   - `DHT-261539E/1#`：合同号 `DHT-261539E`，项目 `Dummar Mall`。
2. **是列被遮住，不是行空白**。横向滚动到最大后，合同号、项目名称、台数、金额、排产完工日期、整梯发货日期都被推到左侧固定列下面；可见区域只剩预计发货日期及之后的列。
3. 伊拉克 9 条记录本身没有预计日期、实际发货日期、订舱审核，所以可见列大多是「—」，视觉上就像整行空白。
4. 1366×768 下滚动到最右时，表头还会被切成残片，例如只显示一个「期」字；用户无法判断当前列是什么。
5. 在 1600×900 下滚动到伊拉克行，数据仍存在，但同样存在「关键列被固定列遮住、表头残片」的问题。

结论：ST-PENDING-03 / 08 的根因是**表格总宽 1912px 远超可视宽度，固定列覆盖了滚动中的前几列，且没有列级信息层级设计**；不是接口漏返回，也不是数据缺失。

## 3. ST-PENDING-03 / 08：横向滚动后“空白行”和表头残片

### 3.1 现象

- 一页 50 条，向下滚到伊拉克模块，再拖动横向滚动条，行内除了模块、梯号外大面积空白。
- 拖到最右时，表头只显示「期」等残字，无法识别列名。
- 合同号、项目名称、台数、金额等列完全消失。

### 3.2 已确认原因

- 左侧固定列宽 381px，右侧固定列 78px，合计 459px 覆盖在滚动内容之上。
- 表格内容总宽 1912px，1366 屏幕可视 1220px，扣除固定列后真正能滚动展示的非固定区域只有约 761px。
- 滚动到最大时，前 6 个非固定列都被压到固定列下面，只剩后半段日期列；伊拉克行这些日期又大多是「—」。
- Element Plus 的固定列使用 sticky 单元格，表头单元格也会被固定表头覆盖，因此出现「期」这种残片。

### 3.3 建议方案（待确认）

不做“继续调小固定列宽度”的补丁，直接重规划主表列：

**默认主表列（建议）**

| 列 | 宽度 | 说明 |
|----|------|------|
| 模块 | 110，固定 | 保持固定 |
| 梯号 | 165，固定 | 保持固定 |
| 合同 / 项目 | 220 | 两行：合同号 + 项目名称，避免两列各占 135/200 |
| 台数 | 50 | 右对齐 |
| 预计发货 | 100 | 缺失显示「未定」而不是「—」 |
| 实际发货 | 100 | 缺失显示「未发」 |
| 订舱 | 110 | 两行：已订舱/未订舱 + 审核状态 |
| 追踪状态 | 90 | 原「当前状态」 |
| 详情 | 56 | 原「历史」改成「详情」，打开抽屉 |

默认列合计约 1001px（管理员多一个 46px 选择列），1366 屏幕无需横向滚动；合同/项目不会再被固定列遮住。

**次级字段**收进「详情」抽屉：金额(万元)、排产完工日期、整梯发货日期、计划变更次数、异常标记、全部操作记录。需要对比时再展开，不占主表宽度。

**备选**：保留横向滚动，但把「合同 / 项目」提升为固定列（固定区变为 601px，1366 屏幕只剩约 619px 给其余列，仍不理想），因此不推荐。

## 4. ST-PENDING-04：计划模板 / 订舱模板按钮

### 4.1 现象

追踪明细面板右上角有「计划模板」「订舱模板」两个按钮，业务不知道它们和当前表格有什么关系。

### 4.2 已确认原因

这两个按钮调用的是导入模板下载接口，和追踪明细没有直接关系；导入管理页已经各自有「下载模板」入口。

### 4.3 处理建议

- 从追踪明细工具栏移除这两个按钮。
- 保留导入管理页的「下载模板」，并补一句用途说明：「首次导入或模板字段变更时下载」。

## 5. ST-PENDING-05：历史按钮与历史字段

### 5.1 现象

- 每行最右侧有「历史」按钮，业务不清楚它记录什么。
- 打开后表格列是：时间 / 类别 / 动作 / 操作人 / 原因 / 变更值。
- 实际内容示例：
  - 类别：`plan`
  - 动作：`add`
  - 变更值：`{"expected_ship_date":"2026-11-04"}`

### 5.2 已确认原因

- `st_audit_log` 存的是内部代码（`plan` / `weekly` / `daily` / `import`，`add` / `update` / `submit` 等）。
- 前端直接输出 `JSON.stringify(new_values)`，没有做中文映射和差异展示。

### 5.3 处理建议

- 按钮改名「详情」或「记录」，放在行内固定位置；打开后同时展示该梯号全部字段和操作记录。
- 类别映射：`plan → 计划导入`、`weekly → 周填报`、`daily → 每日实发`、`import → 导入批次`。
- 动作映射：`add → 新增计划`、`update → 计划变更`、`remove → 计划移除`、`submit → 提交周计划`、`withdraw → 撤回`、`adjust → 同周改期`、`draft_save → 保存草稿`、`create_shipment → 录入实发`、`admin_void_shipment → 作废实发`、`admin_unlock → 管理员解锁`、`commit_plan → 生效计划版本`、`commit_booking → 更新订舱状态`。
- 变更值改成可读文本，例如：
  - 预计发货：`2026-11-04 → 2026-11-09`
  - 排产完工：`空 → 2026-11-05`
  - 模块：`土耳其 → 伊拉克`
  - 实发日期：`空 → 2026-11-03`
- 没有记录时显示「暂无操作记录」，不再显示一行空 JSON。

## 6. ST-PENDING-06：订舱状态 / 订舱审核为什么是空

### 6.1 当前数据核对（数据库实测）

- 订舱批次 3 已生效：文件 `订舱申请流程报表（首页）.xlsx`，316 条有效行、308 个唯一梯号。
- 匹配当前 2026-11 计划 176 个梯号；其余 631 个计划梯号在报表中没有记录。
- 176 个已匹配梯号：143 条审核状态「审批中」，33 条「已完成」。
- 631 个未匹配梯号：订舱状态「未订舱」，订舱审核为空字符串（页面显示「—」）。
- 伊拉克 9 条记录全部不在本次订舱报表中，所以显示「未订舱 / —」。

### 6.2 结论

订舱导入本身是成功的，不是导入失败。用户看到“空”有三个原因：

1. 本次订舱报表只覆盖 176 个计划梯号，其余按设计显示「未订舱」。
2. 未订舱行的「订舱审核」为空，页面用「—」表示，视觉上像空值。
3. 订舱两列在表格右侧，需要横向滚动才能看到；滚动后又容易被固定列遮住（ST-PENDING-03）。

### 6.3 处理建议

- 合并为一列「订舱」，两行显示：第一行「已订舱 / 未订舱」，第二行审核状态；未订舱时第二行显示「无订舱记录」而不是空白。
- 在导入预览和追踪页增加一句口径提示：「本次报表匹配 176 / 807，未匹配按未订舱处理」。
- 如业务希望“报表里没有 = 未知”而不是“未订舱”，需要单独确认口径；当前实现按已文档化的「未订舱」处理。

## 7. ST-PENDING-07：1366×768 下分页被推出首屏

### 7.1 现象

1366×768 屏幕下，表格顶部约在 635px，表格高度按 `window.innerHeight - 390` 计算并夹在 420–760，表格底部超过 1050px；分页在首屏之外，必须滚动页面才能翻页。

### 7.2 已确认原因

`FullTracking.vue` 的 `updateTableMaxHeight()` 只用窗口高度减固定值 390，没有考虑表格实际顶部位置、筛选区高度变化和统计卡片换行。

### 7.3 处理建议

- 用表格容器距视口顶部的实际距离计算可用高度，或改成 flex 布局让表格区域自动占满剩余空间。
- 验收标准：1366×768、1600×900、1920×1080 三档下，分页都在首屏可见；表格至少显示 8 行。

## 8. 已实施事项（2026-11-03 上午）

### 8.1 ST-PENDING-01：底部空白带

- `TrackingTable.vue`：`el-table` 由固定 `:height` 改为 `:max-height`。
- `FullTracking.vue`：`tableHeight` / `updateTableHeight` 改名为 `tableMaxHeight` / `updateTableMaxHeight`，计算逻辑不变。
- 固定列保持「模块、梯号」，未增加合同号固定列。
- 验收：行数少时表格按内容收缩；行数多时封顶滚动。新列方案落地后需要重新回归。

### 8.2 ST-PENDING-02：预计发货日期口径

- 取数顺序改为：L「业务预计发货时间」→ K「7日前发货」→ 留空。
- J「整梯发货日期」和台账 `whole_ship_date` 不再作为预计日期兜底；整梯发货日期只取台账。
- 增加 `expected_from_seven_day` 标记；周填报页提示「7日前发货作为预计日期」。
- 2026-11 计划已按新口径重导为版本 2：814 行 / 807 唯一梯号 / 807 台；预计日期有值 203 条（L 82、K 121），缺失 604 条。
- 样例：`DHT-261406T/3#` 预计 2026-11-09、整梯 2026-10-19；`DHT-261510T/7#` 预计为空、整梯 2026-11-09。

## 9. 已确认方案（2026-11-03）

业务确认结果：

1. **主表采用列设置开关**：默认精简列，用户可在「列设置」中自行勾选金额、排产完工日期、整梯发货日期、计划变更/异常等次级列。
2. **默认主表列**：模块（固定）、梯号（固定）、合同/项目（两行合并）、台数、预计发货、实际发货、订舱（状态+审核两行）、追踪状态、详情。
3. **「历史」合并为「详情」**：行尾按钮改为「详情」，打开右侧抽屉；上半部分展示梯号全部字段，下半部分展示中文操作记录。
4. **未订舱行的订舱审核继续显示「—」**，但订舱列合并为两行，避免被误认为整列空值。
5. **订舱报表未覆盖的计划梯号仍按「未订舱」处理**，与现有文档和导出口径一致；页面增加匹配数量提示。
6. 次级列默认关闭；用户勾选后表格允许横向滚动，固定列仍为「模块、梯号」。
7. 预计发货缺失显示「未定」，实际发货缺失显示「未发」，避免伊拉克等模块因大量「—」被误认为空白行。

- 同一人解析出多个模块时逐个写入，`seen` 按 `(user.id, module_name)` 去重；
- 同一人在文件里写多行不同模块，按人合并统计，报告里标明「N 人对应多个模块，已全部写入」；
- 返回消息与报告增加「写入 X 条（原有 Y 条）」，导入前可对比；

### 16.2 「已提交待发货」筛选为 0

两个原因：

1. 库里从未有人点过「提交下周计划」，旧口径只认 `commit_status='committed'`，所以为 0。按用户确认的新口径：**未发货且已有预计发货日期（计划导入自带或业务填写）就算已提交待发货；没有预计日期才是待安排**。`_tracking_dict` 改为 `elif expected or item.commit_status == 'committed'`，优先级仍是 已发货 > 计划已移除 > 已逾期 > 已提交待发货 > 待安排。
2. 真实缺陷：前端多选把状态用逗号拼成一个 `status` 参数，后端 `getlist('status')` 拿到 `'committed,overdue'` 不再拆分，**多选状态永远为 0**。`blueprint.py::_filter_args` 现在把 `status` / `statuses` 都按逗号拆开。

当前 807 条数据的新分布：已提交待发货 154、已逾期 49、待安排 604。

文案同步：卡片副标题「已有预计发货日期 / 无预计发货日期」；状态筛选悬浮说明改为新口径。周填报「我已提交 / 待发货」区仍只显示真正点过提交的梯号，与全量追踪展示口径不同，属业务需要的区分。

### 16.3 候选表跨页勾选丢失

`el-table` 选择列缺少 `reserve-selection`；表格绑定 `pagedCandidates`（翻页时 `slice` 出的新数组），Element Plus 判定数据实例变化后自动 `clearSelection()`。处理：
