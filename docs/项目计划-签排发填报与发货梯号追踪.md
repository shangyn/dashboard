# 项目计划：单月签排发填报 + 发货梯号追踪

**版本**：v0.1（草稿，待需求方确认）
**日期**：2026-09-23

---

## 0. 一句话概述

这两个项目是一条链子的前后两段：

- **项目 A（已上线）**——解决「**下个月打算发多少台**」：各模块模主按月填报签单 / 排产 / 发货预计。
- **项目 B（待建）**——解决「**这些梯子最后有没有按时发出去、为什么没发、接下来一周能发多少**」：以**梯号**为单位追踪执行状态，并与预测做比对。

A 产出「预测（承诺）」，B 采集「实际」并做比对，最终给领导一个实时的发货望远镜。

---

## 1. 业务背景与目标

### 1.1 背景

现在的流程是：计划员每月把各模块的签排发计划收集起来，汇总成一份 Excel
（当前实例：`数据源/9月签、排、发货计划新.xlsx`，含「汇总」和「发货明细」两张表）。
问题有两个：

1. **收集靠人**：每月月底催各模块模主报数，来回改，汇总靠手工，明细只有计划员手里那一份。
2. **报完就断线**：计划报上去以后，这些梯子到底发没发、几号发的、卡在哪、为什么卡，
   没有任何系统承载，全靠人工问、人工翻台账。

### 1.2 目标

| 项目 | 目标 | 成功标志 |
|------|------|----------|
| A 单月签排发填报 | 让模主自己在系统里按月填报并提交，系统自动汇总、留痕、导出 | 模主无需再交 Excel；汇总数据随时可查、可导出 |
| B 发货梯号追踪 | 以梯号为单位，实时呈现发货状态、延误情况、原因，并给出未来一周预测 | 领导打开页面就能看到「哪些该发没发、为什么、下周预计能发几台」 |

### 1.3 不在范围内（本次不做）

- 不做生产 / 采购 / 制造环节的数据采集（那是工期统计表的领域，本项目只读它）。
- 不做财务口径的应收账款核销。
- 不改动既有「合同完成情况」「工期统计」等模块的数据与逻辑，只读其数据。

## 2. 项目 A：单月签排发填报（已上线）

### 2.1 已实现能力

| 能力 | 说明 | 入口 |
|------|------|------|
| 模块月度填报 | 签单台数/金额、排产台数/金额、发货（候选勾选 + 无梯号手工预估） | 单月签排发填报页 |
| 发货候选池 | 按模块列出「已排产、未发货、未作废」的台账梯号，供勾选 | 填报页下半部 |
| 手工梯号补录 | 候选池里查不到的梯号可手工录入 | 填报页候选区 |
| 无梯号预估 | 还没签、没排产但确定要发的量，手工填台数 + 金额 | 发货卡片 |
| 草稿与提交 | 可反复保存草稿；提交生成本版快照，历史可追溯 | 顶部「保存草稿 / 提交」 |
| 模块名单管理 | 管理员逐条增删「账号 ↔ 模块」归属，支持一人多模块、清理无效归属 | 顶部「名单管理」 |
| 名单批量导入 | 上传 DT号+人名（可带模块列），全量重建归属 | 顶部「导入名单」 |
| 只读汇总 | 无模块归属的账号（含管理员）可看全部模块汇总 | 自动判定 |
| 导出① | 预计签排发台数金额（按模块） | 顶部按钮 |
| 导出② | 预计发货合同号梯号明细 | 仅只读账号可见 |

### 2.2 数据落点（本模块自己的 4 张表）

| 表 | 内容 |
|----|------|
| `mf_monthly_input` | 模块 × 月份 的签单/排产/无梯号预估数值 + 状态 |
| `mf_ship_selection` | 勾选或手工录入的发货梯号明细（含台数、金额快照） |
| `mf_submission` | 每次提交的版本快照（可追溯） |
| `mf_user_scope` | 账号 ↔ 模块 归属名单 |

只读依赖：`cc_ledger_contract`（台账）、`cc_country_mapping`（国家→模块/大区）、`cc_trade_module_data`（商贸）。

### 2.3 已知边界（后续可优化项）

1. 「导入名单」是全量替换，会覆盖手工增删的归属，属破坏性操作。
2. 一人多模块只能通过「名单管理」手工加（走名单导入会被整条略过）。
3. 员工离职删账号后，`mf_user_scope` 会留下孤儿行，需手工点「清理无效归属」。
   - 治本方案：在用户管理的删除逻辑里顺手清理（小改动，尚未做）。
4. 导出②（预计发货明细）不含「无梯号手工预估」，因此它的合计可能小于导出①的发货列。
5. 没有操作留痕（谁在什么时候改了归属，没有日志）。

## 3. 项目 B：发货梯号追踪（待建）

### 3.1 目标用户

| 角色 | 关心什么 |
|------|----------|
| 公司领导 | 哪些梯号该发没发、延误多久、什么原因；未来一周能发多少台 |
| 模块模主 / 业务 | 我名下这个模块的梯号现在到哪一步了，有没有卡住 |
| 生产 / 计划 / 物流 | 排产日期、订舱日期有没有落实，需要提前准备什么 |
| 项目发起人 | 预测准不准，哪个模块报得离谱 |

### 3.2 核心场景

1. **领导视角**：打开页面 → 看到「本月应发 / 已发 / 未按时发」三个数，未按时发的按延误天数排序，点开看原因和当前节点。
2. **日报视角**：专人每天把当天实际发货的梯号录进系统（或导入），系统自动更新状态。
3. **预测对比**：把「A 项目里勾选的预计发货梯号」与「实际发货记录」逐梯号比对，算出预测命中率和偏差。
4. **未来一周**：结合排产完工日期、订舱状态、历史按期率，给出未来 7 天预计能发的台数 / 金额。

### 3.3 功能设计（草案）

**B1 梯号追踪台账（核心）**

以「合同号 + 梯号」为主键，一行一个梯号，聚合展示：

| 字段组 | 内容 | 来源 |
|--------|------|------|
| 基础 | 合同号、梯号、项目名称、模块、大区、业务员 | 台账 / 映射表 / 计划表 |
| 计划 | 排产完工日期、预计发货日期 | 计划表 / 台账排产日期 |
| 实际 | 实际排产日期、订舱日期、实际发货日期 | 台账 / **待确认** |
| 状态 | 未排产 / 已排产 / 已订舱 / 已发货 / 延误 | 计算 |
| 回款 | 已回款金额、回款比例、未回款金额 | 回款明细表 |
| 延误 | 预计 vs 实际差几天、是否超期、超期天数 | 计算 |
| 原因 | 未按时发货的原因、责任节点 | 工期表 reject_reason + **人工填写** |

**B2 每日实发填报**

- 专人每天填写当天发货的梯号（预计按「导入 + 手工补录」两种方式）。
- 需确认：填哪些字段（实际发货日期、订舱日期、异常原因？）、谁能填、能否修改历史。
- 权限建议复用现有 `mf_user_scope` 名单机制：有归属的人只能填自己模块，管理员填全部。

**B3 预测 vs 实际比对**

- 比对对象：A 项目 `mf_ship_selection` 里本月的预计发货梯号 vs B 项目的实际发货记录。
- 输出：本月应发 N 台 / 已发 M 台 / 未发 / 逾期未发；按模块出「按计划发货率」。
- 需确认：比对的时间口径（按月的预测对按月的实际，还是滚动 30 天）。

**B4 未按时发货原因**

- 自动部分：从工期统计表取节点、拒收原因、各节点延误天数。
- 人工部分：专人填写的原因分类（如：未订舱、生产延期、客户原因、单证问题）——**原因分类清单需要你提供**。

**B5 未来一周预测**

- 输入：已排产未发货的梯号 + 排产完工日期 + 订舱状态 + 历史按期率。
- 输出：未来 7 天每天预计发货台数 / 金额，按模块/大区拆分。
- 需确认：预测规则（是不是简单按「排产完工日 + 固定天数」推算？还是需要人工确认）。

**B6 导出与提醒**

- 导出「梯号追踪明细」Excel。
- 可选：超期未发货的每日提醒（推送给谁需要确认）。

### 3.4 数据来源盘点

**已经有的（系统内）**

| 数据 | 位置 | 备注 |
|------|------|------|
| 排产日期、实际发货日期、产品状态 | `cc_ledger_contract`（台账，每日全量替换） | 梯号级 |
| 回款明细（节点类型、金额、日期） | `cc_payment_collection` | 合同 + 梯号级 |
| 生产各节点、拒收原因、排产完工日 | `cc_schedule_tracking`（工期统计） | 梯号级，有延误天数 |
| 模块级签排发计划 | `数据源/9月签、排、发货计划新.xlsx`「汇总」 | 与 A 项目填报同口径 |
| 梯号级预计发货计划 + 回款 | 同上「发货明细」 | 含标的编号、排产完工日期、预计发货日期、回款 |
| 各模块预计发货梯号（填报结果） | `mf_ship_selection` | A 项目产出 |

**目前缺的**

| 缺什么 | 影响 | 需要你确认 |
|--------|------|------------|
| **订舱日期** | 你提到的追踪项之一，全系统目前没有任何字段或数据源 | 从哪来？谁填？还是从某个系统导出？ |
| **每日实发填报的字段与规则** | 决定了 B2 怎么做 | 见第 7 节 |
| **延误判定口径** | 决定「超期」怎么算 | 见第 7 节 |
| 梯号级的历史状态留痕 | 台账是每日全量替换的快照，改了就看不到昨天 | 是否需要每日快照表 |


- 台账 / 映射表 / 回款 等只读数据源

阶段建议：

| 阶段 | 内容 | 产出 |

## 5. 影响面与风险

| 风险 | 说明 | 应对 |
|------|------|------|
| 数据源不稳定 | 台账、工期表靠人工上传，漏传就会导致状态不准 | 页面显著位置显示「数据截止时间」，过期告警 |
| 台账是全量替换 | 昨天已发货的梯号如果今天台账里被改动，历史状态就没了 | Phase 1 里加每日快照留痕表 |
| 梯号匹配不上 | 计划表用「标的编号」，台账用「梯号」，两边写法可能不一致 | 先做匹配率测试，不上的记入异常报告 |
| 每日填报靠人 | 没人填就没数据 | 每日提醒 + 页面显示「今日未填报」 |
| 预测口径争议 | 「未来一周能发多少」算得不准会被质疑 | 先只做「按排产完工日推」，并明确标注是推算值 |
| 两个大区改革 | 大区/模块正在调整（见既有影响面文档） | B 项目所有大区/模块都走动态取值，不硬编码 |

## 8. 待确认问题（需要你拍板）

1. 项目 B 是**独立新页面**，还是挂在「单月签排发填报」页面里做一个新 Tab？
2. 每日实发填报是**填表**（系统内表单），还是**上传 Excel**，还是两者都要？
3. 已经填报提交过的历史月份（A 项目）要不要补录进 B 的追踪范围？
4. 「未来一周」是自然周（周一到周日）还是滚动 7 天？
5. 数据的可见范围：普通模主只能看自己模块，还是所有人可以看全部（只读）？
6. 项目 B 要不要现在就把「两个大区改革」一起考虑进去（大区名会变）？
