# 发货梯号追踪模块 — 服务器更新步骤


> 2026-11-05 更新：本次三角色回归已通过 112 项用例、基线 33/33。上线前请同时执行
> `docs/发货梯号明细-正式服务器上线检查清单-2026-11-05.md`，其中包含有效实发唯一索引
> `uq_st_daily_shipment_active` 的创建与验证步骤。

适用场景：服务器上已有本项目在运行，本次新增「发货梯号追踪」模块，并把合同台账 BN 列「已回款比例（原币）」接入「回款比例」字段。

## 结论

除了代码更新，上线时需要完成五件事：

1. **重新构建并覆盖 `frontend/dist`**（前端构建产物不在 git 里）。
2. **重启后端服务**（启动时才会注册新蓝图、创建 `st_` 表、补菜单权限）。
3. **给相关人员分配权限**（新增了「发货梯号实发」角色）。
4. **重新上传最新合同台账**（`数据源/国贸合同标的台账(92).xlsx`），让 BN 列回款比例写入生产库；上传成功会自动同步到已追踪梯号。
5. **从「回款计算」页签上传表 B、表 E、表 R、汇率 txt，再点击「计算回款」**；这四个业务文件不在代码包中。

不需要：

- 不需要安装新的 Python 包（模块使用项目已有的 Flask/SQLAlchemy/openpyxl/pandas）。
- 不需要手工执行建表 SQL（服务启动时自动创建 10 张 `st_` 表）。
- 不需要修改端口和防火墙；但要确认 Nginx 的 `client_max_body_size` 足够大，建议至少 `100m`，否则大文件上传会被 Nginx 以 413 拦截，应用不会收到请求。
- 不需要把开发机的数据库拷到服务器，**千万不要覆盖生产库**。

### 服务器现场构建前端时还需要

- `frontend/src/router/index.js`
- `frontend/src/api/shipTracking.js`
- `frontend/src/views/ship_tracking/`：整个目录，5 个文件。

### 同工作区已有、但不属于本模块运行依赖的改动

- `backend/monthly_forecast/handlers.py`
- `backend/monthly_forecast/services.py`
- `frontend/src/views/MonthlyForecast.vue`

这些文件只在本次发布同时包含单月填报相关修正时一起上传；不要误认为缺少它们会导致发货梯号模块启动失败。

- `backend/instance/system.db`：生产数据库，禁止用开发库覆盖。

- `backend/ship_tracking/__pycache__/`、`tmp_ui/`、`frontend/node_modules/`。
- `数据源/` 和任何测试 Excel/CSV；业务源文件通过页面后台上传。
- `backend/dashboards/Project_Schedule` 当前工作区是脏子模块，除非已确认其内容，否则不要随包上传。

## 1. 服务器备份数据库

更新前先备份生产库，避免意外：

```bash
cd /path/to/dashboard

# 推荐：SQLite 在线备份，服务不用停
sqlite3 backend/instance/system.db \
  ".backup 'backend/instance/system.db.bak-$(date +%F-%H%M)'"

# 没有 sqlite3 命令时用 Python
python3 - <<'PY'
import sqlite3, datetime
src = sqlite3.connect('backend/instance/system.db')
dst = sqlite3.connect('backend/instance/system.db.bak-' + datetime.datetime.now().strftime('%Y%m%d-%H%M%S'))
src.backup(dst)
dst.close(); src.close()
PY
```

## 3. 构建前端（必须）

`frontend/dist` 不在 git 里，不重新构建会出现：

- 侧边菜单能看到模块，但点进去 404 / 白屏；
- 或仍是旧页面，没有「发货梯号追踪」入口。

### 方式 A：服务器有 Node.js

```bash
cd /path/to/dashboard/frontend
npm install
npm run build
cd ..
```

要求 Node.js 20 或 22 LTS。项目没有提交 `package-lock.json`，所以用 `npm install`，不要用 `npm ci`。

### 方式 B：服务器没有 Node.js，在开发机构建后上传

开发机（Windows PowerShell / Git Bash）：

```bash
cd E:/System/frontend
npm install
npm run build

# 用 rsync 覆盖服务器 dist（示例路径按实际替换）
rsync -av --delete frontend/dist/ user@SERVER:/path/to/dashboard/frontend/dist/
```

或直接用 WinSCP 把整个 `frontend/dist` 覆盖到服务器同名目录。

确认服务器上存在：

```bash
ls frontend/dist/index.html
```

## 4. 重启后端服务

模块的建表、菜单和权限都在应用启动时执行，必须重启，不能只 reload 页面。

按现有部署方式选择：

```bash
# systemd
sudo systemctl restart <你的服务名>
sudo systemctl status <你的服务名>

# supervisor
sudo supervisorctl restart <你的程序名>

# 如果是 gunicorn 手工启动，按原来的启动命令重新拉起
```

启动日志里应能看到 `[ShipTracking] ...` 相关输出；没有报错即可。

## 5. 启动时自动完成的事情

不需要手工操作，服务启动后会自动：

- 创建 10 张表：
  `st_import_batch`、`st_import_issue`、`st_plan_item`、`st_tracking_item`、
  `st_daily_shipment`、`st_booking_record`、`st_audit_log`、
  `st_payment_file`、`st_payment_calc_run`、`st_payment_calc_detail`
- 注册「发货梯号追踪」菜单，地址 `/ship-tracking`
- 给管理员、查看上传、仅查看不上传角色追加查看权限
- 创建「发货梯号实发」角色
- 为 `cc_ledger_contract` 幂等补 `payment_ratio` 列（仅加列，不清空既有台账）
- 为 `st_tracking_item` 幂等补 `payment_ratio` 列；首次上线会尝试从现有台账回填
- 为 `st_tracking_item` 幂等补 `actual_ship_source` 列，并在首次上线后按台账组A日期回填实际发货日期
- 自动创建回款文件目录 `backend/uploads/ship_tracking/payment_calc/`
- 为 `st_daily_shipment` 创建 `uq_st_daily_shipment_active` 唯一索引

> 旧生产台账没有 BN 列数据，启动后的首次回填可能为空。必须按第 7 节验证清单重新上传最新台账，回款比例才会完整显示。

> 实际发货日期口径：台账「组A日期」优先；台账没有时保留每日实发日期；两边都有时以组A日期为准。页面来源标注为「台账」或「系统」。

可用下面的命令确认表已创建：

```bash
sqlite3 backend/instance/system.db \
  "SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'st_%' ORDER BY name;"
```

应返回 10 张表。表是空的，属于正常；计划数据由管理员在页面上导入。

## 6. 分配权限

- **管理员**：自动获得全部权限。
- **查看上传 / 仅查看不上传**：自动获得查看权限。
- **发货梯号实发**：启动时自动创建角色，但需要到「用户管理」把具体人员分配到这个角色。
- **单月签排发填报**：只获得模块入口，不自动获得全量查看或实发权限，按需单独分配。
- **导入管理**：不再要求管理员；所有能看到全量主页面的角色都可打开，接口权限已同步放开。

不要让业务填报人员拿到「发货梯号实发」角色，否则他们可以录入实发数据。

### 6.1 模块人员名单说明

发货梯号追踪**没有独立名单**，直接复用「单月签排发填报 → 名单管理」里的 `mf_user_scope`。现有名单不需要为上线重新导入。

需要关注三点：

1. **实发人员必须是独立账号**：`发货梯号实发` 角色要求账号没有模块归属。如果账号已在 `mf_user_scope` 中，系统会关闭全量查看和每日实发权限。且一个账号只有一个角色，不能同时承担单月填报和实发。
2. **查看角色保持无模块归属**：`管理员`、`查看上传`、`仅查看不上传` 才能看全量数据；一旦给这些账号加了模块归属，会退化成只看自己模块的填报视图。
3. **7 个模块当前无人归属**（按 807 条计划实测，共 236 条梯号）：
   `埃及-1`(204)、`乌兹别克斯坦（工厂）`(9)、`智利`(7)、`巴勒斯坦`(6)、`阿联酋-1`(6)、`孟加拉`(3)、`伊朗`(1)。
   如果这些模块需要业务人员周填报，要在「单月签排发填报 → 名单管理」补人；补人同时会获得该模块的单月填报权限。若不补，只有管理员和查看角色能看到这些梯号。

## 7. 验证清单

1. 管理员登录，左侧出现「发货梯号追踪」。
2. 打开 `/ship-tracking`，页面正常加载（不是旧页面/404）。
3. 「导入管理 → 月度计划」上传 `11月梯号发货明细.xlsx`，预览应为：
   - 源数据行 814、唯一梯号 807、重复组 7
   - 警告 132、错误 0
   - 表头识别为「新格式（业务预计发货时间）」、11 列
4. 确认导入后，全量追踪显示 807 条。
5. 「导入管理 → 合同台账」上传最新 `数据源/国贸合同标的台账(92).xlsx`；上传结果中的 `ship_tracking_sync` 应为 `ok`，并记录 `ratio_changed`。
6. 全量明细确认「回款比例」位于「订舱状态」后，显示两位小数；`100%` 筛选只显示满额行，`其他` 包含未满 100%、0% 和台账未匹配行，两者合计等于总数。
7. 「下载明细 Excel」能正常下载，含「发货明细」「发货汇总」两页，第 16 列为回款比例。
8. 需要订舱状态时，再导入 `订舱申请流程报表（首页）.xlsx`。
9. 用实发角色账号登录一次，确认能看到「每日实发」页签。
10. 其他模块（单月签排发填报、合同看板等）打开正常。
11. 进入「回款计算」，上传表 B、表 E、表 R、汇率 txt，四张卡片均显示「已校验」。
12. 点击「计算回款」，状态从「计算中」变为「计算成功」；主明细回款比例更新。
13. 验证「100% / 其他」筛选、明细导出和回款审计下载均正常。
14. 用非管理员查看角色登录，确认能看到「导入管理」和「回款计算」，且导入批次、同步状态接口返回 200。

## 9. 常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 菜单没有「发货梯号追踪」 | 没重启后端，或代码没 pull 到 | 重启服务，确认 `backend/ship_tracking/` 存在 |
| 点菜单 404 / 白屏 | `frontend/dist` 没重新构建 | 执行第 3 步 |
| 提示 `Frontend not built` | 服务器上没有 `frontend/dist` | 构建或上传 dist |
| 导入报“未找到表头” | 文件不是约定的 A–K 格式 | 使用 `11月梯号发货明细.xlsx` |
| 导入报“缺少合同号/梯号” | 表头被改名或删列 | 恢复标准表头 |
| 启动报数据库只读/无法建表 | 服务用户对 `backend/instance` 无写权限 | `chown` 给运行服务的用户 |
| 多人同时写入偶发 database is locked | SQLite + 多 gunicorn worker | 生产建议 workers 降到 2，或开启 WAL/加 busy_timeout |
| 页面能开但接口 CORS 报错 | 前端和 API 不同源，且新域名不在白名单 | 在 `backend/app.py` 的 CORS origins 中加入实际访问地址 |
| 回款比例为空 | 未重新上传含 BN 列的最新台账，或该梯号未匹配台账 | 上传最新合同台账并点击「立即同步」；核对 BN 列和梯号 |
