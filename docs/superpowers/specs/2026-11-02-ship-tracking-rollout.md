# 发货梯号追踪 - 上线说明（2026-11-02）

## 已实现范围

- 独立后端模块：`backend/ship_tracking/`，只新增 `st_*` 表。
- 独立前端模块：`frontend/src/views/ship_tracking/`，入口 `/ship-tracking`。
- 月度计划 Excel：流式解析当前激活的预计发货明细表，不加载外部链接缓存。
- 订舱报表：按 AG 列匹配完整梯号，C 列审核状态单独展示。
- 业务下周填报：逐梯号选择下周日期，支持批量套用日期、草稿、提交、同周改期/撤回。
- 多模块填报：同一账号归属多个模块时，可查看「全部我的模块」或单独切换；跨模块可一次提交，提交后从候选池隐藏。
- 每日实发：独立角色批量录入；日期不得晚于今天，历史补录填写原因。
- 全量追踪：所有非「单月签排发填报」查看/管理角色可看全部模块，支持筛选和 Excel 导出。
- 追踪明细：左侧只固定「模块、梯号」，表格使用最大高度自适应并常显横向滚动条；模块升序、模块内预计发货日期倒序。
- 月中重导计划：新计划生成新版本；实发、订舱事实不删除；已提交承诺不静默覆盖，进入冲突标记。
- 本期不包含回款字段、回款上传或回款比例计算。

## 启动时自动完成的配置

1. 创建缺失的 `st_*` 表，不修改 `cc_*` 和 `mf_*` 表结构。
2. 创建菜单「发货梯号追踪」，URL `/ship-tracking`，权限 `ship_tracking`。
3. 为现有角色**追加**权限，不删除原权限：
   - 管理员：`ship_tracking`、`ship_tracking_view`、`ship_tracking_admin`
   - 查看上传：`ship_tracking`、`ship_tracking_view`
   - 仅查看不上传：`ship_tracking`、`ship_tracking_view`
   - 单月签排发填报：仅 `ship_tracking`
4. 创建角色「发货梯号实发」，权限为 `ship_tracking`、`ship_tracking_view`、`ship_tracking_daily_edit`。
   - 不自动创建账号，也不自动分配人员。
   - 必须单独给实发人员分配该角色，不能与业务填报人员复用。
5. 如果数据库没有任何已提交计划，首次启动自动导入仓库根目录的
   `2026-11_预计发货合同梯号明细 (10.28).xlsx`。
   - 预期结果：814 源数据行、7 组重复、807 个唯一梯号、807 台。
   - 可用环境变量 `SHIP_TRACKING_AUTO_BOOTSTRAP=0` 关闭自动导入。
6. 多 Gunicorn worker 启动使用文件锁串行初始化，避免重复导入或权限并发写入。

## 日期字段口径与覆盖情况

「预计发货日期」只取计划 Excel 中业务填写的两列，顺序为：

1. L 列「业务预计发货时间」；
2. L 列没有有效日期时，取 K 列「7日前发货」；
3. K/L 都没有有效日期时留空（页面显示「—」），由业务在周填报时补选。

J 列「整梯发货日期」不再作为预计日期的初值或兜底；它只作为独立展示字段，取值直接来自台账 `cc_ledger_contract.whole_ship_date`，台账为空时显示「—」。台账日期也不再作为预计日期的兜底。

「排产完工日期」优先取计划 Excel I 列，缺失时参考台账表 cc_ledger_contract 的 schedule_finish_date。

基于当前 2026-11 计划（807 个唯一梯号）的源表统计（严格 K/L 口径）：

- 排产完工日期：648 条有值，159 条缺失。
- 预计发货日期：L 有效 82 条，K 有效 125 条，K/L 合并 203 条，缺失约 604 条。
- L 列非空但无法解析为日期的 334 条，其中不少填的是数字 0，其余包括「11月末」「第二周」「急」「业务要求11月5日发货」等；这些记录只有在 K 列有有效日期时才会得到预计日期，否则留空。

台账源文件（国贸合同标的台账(92).xlsx）并不是每个梯号都有整梯发货日期；页面显示「—」代表台账未提供或计划 K/L 未填写，不应理解成系统漏匹配。另有一份执行工期统计表，但不能作为完整兜底来源。

使用 K 列作为预计日期时，记录会带 `expected_from_seven_day` 标记，页面提示「7日前发货作为预计日期」。

### 2. 分配每日实发人员

在「用户管理」中，选择一个独立账号分配「发货梯号实发」角色。该账号不能同时作为业务填报人员使用。

### 3. 核对订舱报表覆盖区间

当前订舱文件只覆盖 2026-10-07 至 2026-10-30，且包含“审批中”状态。系统按以下规则显示：

- 至少一条非作废记录：已订舱
- 无记录或全部作废：未订舱
- 审核状态优先显示已完成，否则显示最新非作废记录，全部作废显示已作废

未出现在本次报表中的梯号会显示“未订舱”，上传页已提示报表覆盖范围限制。

### 4. 月初确认 2026-11 数据基线

首次导入只能确认“计划内 807 个梯号及其源表字段”，不能自动证明计划本身没有漏梯号。上线后请先让各模块负责人确认：

- 本模块计划梯号是否完整；
- 159 条双日期缺失和 318 条无可用预计日期的梯号如何安排；
- 重复 7 组是否确实属于同一梯号。

确认完成后，再以该版本作为 11 月核对基线。

## 月中计划调整如何处理

1. 重新上传计划文件，先进入预览，不直接改数据。
2. 预览显示新增、移除、预计日期变化、模块变化、已提交冲突、已实发后移除、有订舱后移除。
3. 管理员确认后生成新版本。
4. 已实发记录、订舱记录永久保留。
5. 已提交未发货梯号若改期或被移除：
   - 原承诺日期不被覆盖；
   - 标记「计划日期与已提交承诺不一致」或「已提交后计划被移除」；
   - 由管理员在冲突列表中处理或解锁。
6. 旧计划版本和旧导入批次保留，可追溯。

## 11 月准确性闭环

只靠“导入计划梯号 + 业务填预计日期 + 每日录入实发”，系统能发现问题，但不能自动保证 100% 准确。原因有三类：

- 每日实发人员漏录，系统无法知道；
- 月初计划本身漏掉应追踪梯号，系统也无法知道；
- 业务填了格式合法但实际错误的日期，系统只能记录，不能判断真假。

每月至少按以下口径闭环：

1. 每个有效计划梯号必须落到以下一种状态：已实发、已提交待发货、明确本月不发货并填写原因、计划移除并经管理员确认。
2. 每日实发必须与物流/发运日报核对总数和梯号，重点检查计划外实发。
3. 月末生成模块级核对表：计划数、已填日期、已提交、已实发、未发货、计划外实发、异常未闭环。
4. 管理员确认后锁定月度口径；之后修改必须走解锁并留原因。

当前已提供“未填预计日期、下周及逾期未提交、计划外实发、计划移除后实发、异常标记”等预警，以及版本化重导和操作审计；尚未提供“本月不发货原因”“月度确认/锁定”两个闭环功能，建议作为下一阶段补充。

## 部署顺序

1. 备份 `backend/instance/system.db`。
2. 部署代码。
3. 前端执行 `npm run build`。
4. 重启 Flask/Gunicorn。
5. 首次启动检查日志中的 `[ShipTracking]` 行和 807 台导入结果。
6. 检查四个角色权限菜单是否出现。
7. 用管理员进入「导入管理」核对批次、计划版本和订舱匹配。
8. 用一个业务填报账号验证只能看到自己的模块；多模块账号验证「全部我的模块」和跨模块提交。
9. 用实发专用账号验证可看全量、无需二次输入密码即可提交实发。
