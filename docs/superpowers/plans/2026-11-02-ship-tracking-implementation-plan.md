## 0. 已确认的需求

| 决策 | 结论 |
|------|------|
| 模块形态 | 新增独立模块 `ship_tracking`，不修改单月签排发模块 |
| 数据粒度 | 一个梯号一条追踪主记录，不按周复制梯号行；默认一梯一次发货 |

| 主表 | 以现有 Excel 字段为基础，合并重复的预计日期列 |

## 1. 目标与边界

### 1.1 目标

- 业务按周填写下一周预计发货梯号，提交后不会重复出现在以后每周的候选池中。
- 每日由专有角色录入实际发货梯号，形成计划与实际的逐梯号对比。
- 管理人员始终可以看到全量梯号、计划日期、实际日期、当前状态和异常。
- 月度 Excel 可作为全量计划底稿导入，支持补充和纠正单月签排发模块的数据缺口。
- 为后续订舱状态、逾期统计预留稳定的数据结构和页面位置；回款后续单独接入。

### 1.2 本次不做

- 不做按周独立的数据表。周只是日期推导出来的视图，不是一条新的梯号记录。
- 不修改现有 `mf_*` 表及单月签排发模块的历史数据。
- 不在本轮确定回款的上传数量、字段和比例算法。
- 不自动把台账 `product_status=在运输` 当作已发货；实际发货只认每日实发。
- 不做生产、采购、制造环节的重新采集。

## 2. 核心模型：一条梯号主记录

建议新增独立模块 `ship_tracking`，使用 `st_` 表前缀，和现有 `mf_`、`cc_` 表隔离。

### 2.1 三层数据

| 层 | 内容 | 说明 |
|----|------|------|
| 计划层 | 月度计划、业务下周提交 | 同一梯号只保留当前计划日期；历史变化进入变更流水 |
| 执行层 | 每日实际发货 | 专有角色录入；不能被周计划覆盖 |
| 计算层 | 订舱、逾期 | 后置计算；回款后续单独接入 |

### 2.2 业务时间线

```text
月度计划导入 / A模块预计梯号
        ↓
业务在目标周选择梯号 + 预计发货日期
        ↓ 提交
从候选池隐藏，进入我已提交/待发货
        ↓
专有角色每日录入实际发货日期
        ↓
已发货 / 逾期 / 转下周（按实际状态派生）
```

## 3. 角色与权限

| 角色/权限 | 对应页面 | 可见范围 | 可操作 |
|-----------|----------|----------|--------|
| 业务填报 `ship_tracking_fill` | 下周填报页 | 自己模块 | 选择下周梯号、填写预计日期、提交、查看本人已提交；不能进入全量追踪 |
| 全量查看 `ship_tracking_view` | 全量追踪页 | 全部模块、全部历史 | 只读、筛选、导出；仅授予不在单月签排发填报名单中的角色 |
| 每日实发 `ship_tracking_daily` | 全量追踪页 + 每日实发页 | 全部模块 | 查看全部；仅录入/修改实际发货日期、补录计划外实发；不能修改计划 |
| 管理 `ship_tracking_admin` | 导入/管理页 + 全量页 | 全部 | 导入、预览、解锁、批次回滚、异常处理 |

- 业务填报权限与「单月签排发填报」保持一致，复用现有 `mf_user_scope`；有归属的用户只能操作自己模块，无归属但具备全量查看权限的用户只读。

- 不修改 `mf_user_scope` 的历史数据；如需补充，使用现有名单管理入口。
- 业务填报人员和全量查看人员走不同的页面和接口，避免业务填报人员通过菜单或接口看到全部模块。

- 所有写操作记录操作人、时间、批次号和变更前后值。

### 3.4 每日实发角色的查看与写权限

每日实发角色不是只能看自己模块，而是需要查看全部梯号，因此授予两项权限：

- `ship_tracking_view`：查看全量追踪，只读。
- `ship_tracking_daily_edit`：只能写实际发货日期和实发事件，不能修改计划日期、模块、业务归属或周填报锁定状态。

保护设计：

- 不设置共享页面密码。共享密码无法识别具体操作人，会破坏审计。
- 每日实发角色使用个人平台账号登录；权限由管理员分配，不使用公共账号。
- 已确认下周计划填报与每日实发不是同一人员；每日实发使用独立账号，不加入 `mf_user_scope`，不需要兼岗例外。
- 批量提交实发前要求二次确认，并再次输入本人登录密码。
- 修改当天实发日期允许本人操作，但必须填写原因并留痕。
- 修改历史日期、跨天补录或撤销实发，需要管理员解锁/审批。
- 每日实发页显示本批次条数、重复梯号、计划外梯号，确认后才提交。


## 4. 业务流程

### 4.1 月度明细导入

1. 管理员上传 Excel，选择 sheet：固定使用当前激活的 `预计发货明细 (2)`。
2. 系统先解析并预览，不直接写库。
3. 预览显示：可导入行、自动修正行、自动展开行、重复梯号、无效行、日期异常、模块缺失。
4. 管理员确认后按批次入库。
5. 导入批次可查看错误明细；在未被后续业务修改前可按批次回滚。

导入只建立计划底稿，不自动等同于业务已经提交下周计划。除模板明确带提交状态外，导入行默认不是锁定状态。

### 4.2 业务填写下周计划

页面顶部固定显示本次目标周，例如 `2026-11-09 至 2026-11-15`，默认下一个自然周。

候选池规则：

- 只显示当前账号所属模块的梯号。
- 排除已实际发货、已作废、已提交锁定的梯号。
- 默认显示无预计日期、预计日期落在目标周内、或已经逾期未发的梯号。
- 预计日期在更远未来周的梯号，不提前进入本周候选。
- 支持搜索合同号、梯号、项目名称、业务员。

填写规则：

- 主控件使用**预计发货日期**，不是只存“下周发货”的布尔值。
- 提供下周一、下周二、下周五等快捷按钮。
- 支持多选后批量设置日期。
- 日期必须由业务主动选择，不能空着提交；系统只用现有整梯发货日期做预填，不能替业务默认一个日期。
- 日期必须落在本次目标周内；要改到其他周，走“调整到下周/改期”动作并留痕。
- 只能从当月计划中已有梯号中选择，不允许业务新增计划外梯号；计划外梯号只能由管理员补录。
- 先保存草稿；只有点击“提交下周计划”才进入锁定。

### 4.3 提交后的锁定与隐藏

提交动作按批次执行，整批成功或整批失败。提交成功后：

- 该梯号标记为已提交，记录 `committed_week_start`、`committed_at`、提交人和批次号。
- 从下一周的可填报候选池隐藏。
- 仍出现在本人/本模块的“我已提交/待发货”区域。
- 管理人员全局表中始终可见。
- 同一自然周内允许业务撤回或改期；跨周后只能由管理员解锁，并记录原因和操作人。
- 如果下周仍未实际发货，进入“上周未发/逾期”，不会因为上周填写过而丢失。

界面状态建议：

| 界面状态 | 含义 |
|----------|------|
| 未报计划 | 尚未提交下周计划 |
| 已报下周 | 业务已提交，等待发货 |
| 已报排产 | 按业务口径视为进入排产；不冒充生产已排产 |
| 待发货 | 已锁定但未实际发货 |
| 已发货 | 已有每日实发记录 |
| 逾期 | 预计日期已过且未发货 |
| 转下周 | 通过调整动作移到后续周 |

### 4.4 每日实发

- 只由 `ship_tracking_daily` 角色使用。
- 默认发货日期为当天，可修改。
- 支持搜索梯号、合同号，支持批量粘贴。
- 录入后更新主记录的实际发货日期，并保留实发事件。
- 默认一个梯号只发一次；同一梯号重复提交做幂等处理，不产生重复实发。
- 查到计划外梯号时，允许标记为“计划外实发”，不能静默丢弃。
- 台账 `在运输`、`未履行` 等状态只做参考，不自动生成正式实发记录。

### 4.5 全量查看

- 有查看权限的人可以查看全部模块、全部月份、全部状态。
- 默认按月份和模块筛选，但“全部”视图不能被周填报的隐藏规则影响。
- 支持查看：本周应发、已发、未发、逾期、上周遗留、计划外实发。
- 页面显示数据截止时间：最近导入时间、最近每日实发时间、最近订舱数据时间。

## 5. 数据模型

### 5.1 `st_tracking_item`

一个梯号一条主记录，业务键为规范化后的 `ladder_key`。

关键字段：

- `ladder_key`：唯一键，规范化的完整梯号。
- `contract_no`、`ladder_no`、`project_name`、`module_name`、`region`、`salesperson`。
- `owner_user_id`、`owner_username`、`owner_name`：业务归属和 DT 号。
- `unit_count`、`amount_rmb`：金额统一存人民币元，页面显示万元。
- `plan_month`、`plan_version`、`plan_status`、`expected_ship_date`、`original_expected_ship_date`、`committed_expected_ship_date`、`planned_week_start`、`plan_change_count`。
- `commit_status`、`committed_week_start`、`committed_at`、`committed_by`。
- `actual_ship_date`、`actual_source`。
- `booking_status`：本期计算列；回款字段仅预留，本期不展示。
- `source`：`A模块`、`Excel导入`、`手工补录`。
- `data_flags`：台账未匹配、重复、日期异常、计划外等标记。

### 5.2 `st_plan_item`

保存月度计划来源，不按周拆行。

- `plan_month`、`ladder_key`、`source`、`source_batch_id`、`plan_version`、`effective_from`、`record_status`。
- `contract_no`、`ladder_no`、`module_name`、`unit_count`、`amount_rmb`。
- `original_schedule_finish_date`、`original_whole_ship_date`。
- `original_expected_ship_date`、`current_expected_ship_date`、`change_reason`。
- `expected_ship_date_initial`、`validation_status`、`raw_payload`。

用途：保留 Excel 原始计划和 A 模块计划来源，方便对比和重新导入。

### 5.3 `st_plan_revision`

计划变更流水，不是周数据表。

- `ladder_key`、`batch_id`、`action`。
- `old_expected_ship_date`、`new_expected_ship_date`。
- `old_commit_status`、`new_commit_status`。
- `operator_id`、`operator_name`、`changed_at`、`reason`。

用于业务提交、改期、转下周、管理员解锁和批次回滚。

### 5.4 `st_daily_shipment`

- `ladder_key`、`ship_date`、`unit_count`、`operator_id`、`operator_name`。
- `source`、`batch_id`、`remark`。
- 同一梯号默认只保留一次有效实发；如存在分批发货，再用多条事件和汇总逻辑扩展。

### 5.5 导入批次与异常

- `st_import_batch`：文件名、文件哈希、sheet、导入人、时间、状态、统计结果、计划版本、差异摘要。
- `st_import_error`：行号、原始值、错误类型、处理建议。

### 5.6 只读数据源

- `cc_ledger_contract`：合同、项目、模块、排产日期、整梯发货日期等静态信息。
- 本期不接入 `cc_payment_collection`；回款后续单独设计。
- `mf_ship_selection`：单月签排发模块已提交的预计发货梯号。
- 订舱报表：后续导入到 `st_booking_record`，本阶段先不写业务逻辑。

## 6. Excel 导入与清洗

### 6.1 数据源

确认使用 `2026-11_预计发货合同梯号明细 (10.28).xlsx` 的 `预计发货明细 (2)` 当前激活 sheet。

不要使用隐藏的 `预计发货明细` 第一张 sheet。第二张表有效台数合计为 814 台，是第一张表 480 台之外的完整版本。

### 6.2 字段映射

| Excel 列 | 系统字段 | 处理 |
|----------|----------|------|
| A 模块 | `module_name` | 去空格，校验是否为正式模块名 |
| B 合同号 | `contract_no` | 去空格 |
| C 梯号 | `ladder_no` | 生成完整梯号 `contract/ladder#` |
| D 列 | `project_name` / `unit_count` | 前段是项目名称；后段变成台数 1，需要按数据段识别 |
| E 列 | `unit_count` | 前段是台数；后段为空，不能把空台数当成 0 台 |
| F/I/O 金额 | `amount_rmb` | 第二张表追加段列发生错位，优先用梯号到台账取合同额；无台账时再按原始金额和单位识别，冲突写入异常 |
| G 来源 | `source` | 候选勾选 / 手工输入 / Excel导入 |
| H 填报人 | `filler_name` | 保留，尽量映射 DT 号 |
| I 排产完工日期 | `schedule_finish_date` | 日期校验，优先与台账核对 |
| J 整梯发货日期 | `whole_ship_date` | 仅展示，直接取台账 `cc_ledger_contract.whole_ship_date`；台账为空则空，不作为预计日期来源 |
| K 7日前发货 | `expected_ship_date_initial` | 预计日期候选；L 无有效日期时使用 |
| L 业务预计发货时间 | `expected_ship_date_initial` | 预计日期第一优先 |
| M 实际发货日期 | 参考值 | 不作为正式实发主数据 |

主表只保留一列 `预计发货日期`，取数顺序为 L → K；两列都无有效日期时留空，由业务周填报补选。J 单独展示，不参与预计日期兜底，也不再用台账日期兜底。

### 6.3 规范化规则

- 去除前后空格、全角空格和不可见字符。
- 统一全角斜杠、逗号、分号和顿号的分隔符。
- C 列已是完整梯号：直接使用。
- C 列只有后缀且 B 有合同号：补成 `B/C`。
- C 列为 `1-10#`、`14-15#，24-26#` 这类区间：展开为单个梯号，每个梯号一行。
- C 列只有 `10` 这类数字：用 B 补成完整梯号。
- B 为空且无法得到合同号：进入异常，不导入。
- 一个梯号在导入文件中出现多次：确认属于重复导入；按梯号去重，优先保留与台账合同额一致、字段更完整的一行，被丢弃行进入导入报告。
- 模块名为空但能从合同/台账解析：自动补全；解析不到：进入异常。
- 日期为 0、空、`#N/A`、纯数字但无法转日期：按空值或异常处理，不能当成 1900 年日期。
- 金额、台数为空或非法：不默认写 0，进入异常清单。

## 7. 主表与导出

- `计划周` 由预计日期自动推导，不手填。
- `实际发货日期` 只由每日实发更新。
- `订舱状态`、`订舱审核状态` 是本期计算列；回款列本期不出现在主表和导出中。
- 缺失值显示 `—`，不要显示 0，避免把“没有数据”误判成“0 元/未回款”。
- 导出 Excel 保持与主表同样的列和筛选条件。

## 8. 中途调整与项目韧性

### 8.1 核心原则

- 实际发货是事实，不能被月度计划重新导入覆盖、删除或隐藏。
- 月度计划是版本，不是一张可随意覆盖的静态表。
- 业务提交的下周计划是承诺，提交后不能被后台导入静默改掉。
- 订舱是外部事实，按 AG 独立匹配；计划变化不删除已存在的订舱记录。
- 任何变更都要能回答：改了什么、谁改的、什么时候、影响哪些梯号、依据哪次导入。

### 8.2 三层事实

| 层 | 数据 | 处理原则 |
|----|------|----------|
| 事实层 | 每日实发、订舱导入 | 只追加/更新来源快照，不因计划变化删除 |
| 计划版本层 | 月度导入批次、计划明细 | 每次重导生成新版本；保留旧版本和差异 |
| 承诺层 | 业务周提交 | 保留提交快照；后台改计划时产生冲突，不静默覆盖 |

当前页面看到的是“当前计划版本 + 当前实发事实”的派生结果，历史版本仍可追溯。

### 8.3 月中调整场景

| 月初导入后发生的变化 | 预计计划 | 已提交下周计划 | 实际发货 | 订舱 |
|------------------------|----------|----------------|----------|------|
| 新增梯号 | 进入新版本，按预计日期决定何时进入候选池 | 不影响已提交行 | 不影响 | 不影响 |
| 修改预计日期 | 当前预计日期更新，原日期保留 | 已提交行产生冲突，需确认 | 不影响 | 不影响 |
| 删除梯号 | 标记“计划已移除”，不物理删除 | 已提交记录保留并提示取消/转计划外 | 如已实发，仍保留并标记“已从计划移除但已实发” | 不影响 |
| 修改模块/业务员 | 更新归属并重新计算可见范围 | 已提交行提示归属冲突 | 不影响 | 不影响 |
| 修改台数/金额 | 更新当前计划值，保留原始值 | 不改变已提交数量，提示差异 | 不影响 | 不影响 |

### 8.4 重导流程

1. 上传新 Excel，生成新导入批次和文件哈希。
2. 与当前有效计划做差异比较：新增、修改日期、删除、模块变化、金额变化。
3. 预览受影响范围：是否涉及已提交周计划、是否涉及已实发梯号。
4. 管理员确认后生成新的计划版本，旧版本不删除。
5. 通知受影响模块；已提交行进入冲突处理列表。
6. 实际发货和订舱记录不参与计划回滚。

### 8.5 冲突处理

- 已提交、未发货的梯号被改期或删除：不能自动改承诺，显示“计划变更冲突”，由业务确认保留/改期/取消。
- 已实发的梯号被删除：实际记录保留，主表标记“计划外实发/计划已移除”，统计时单独展示。
- 已订舱但计划删除：订舱记录保留，标记为“有订舱无当前计划”，供人工核对。
- 同一文件重复上传：按文件哈希和批次提示重复，不重复生成版本。

### 8.6 指标与历史

- 主表同时保留 `原始预计日期`、`当前预计日期`、`提交时预计日期`、`实际发货日期`。
- 默认运营视图按当前计划算逾期；审计视图可看原始计划和计划变更次数。
- 导出 Excel 至少包含当前预计日期、原始预计日期、变更次数，避免改期后无法追溯。
- 后续如需“某一天的状态”，按 plan_version 和实际事件做 as-of 查询。

### 8.7 韧性结论

如果按本方案做“计划版本 + 差异预览 + 承诺冲突 + 事实不覆盖”，项目可以承受月中频繁调整；实际发货不会因导入变化而受影响。

如果采用“重新上传直接覆盖当前表”的简化做法，月中调整会带来三类风险：已提交计划被静默改掉、删除梯号后实发记录丢失、历史报表无法解释；不建议。
## 9. 防错设计

- 主记录使用 `ladder_key` 唯一约束，禁止同一梯号产生多条主记录。
- 周提交使用批次号，数据库事务保证整批成功或整批失败。
- 重复提交同一梯号同一目标周时更新原记录并记录修订，不新增重复行。
- 业务提交后需要改期/撤回，必须走调整动作；禁止直接改数据库。
- 管理端支持按批次回滚，但只回滚本批次修改，不删除后续实际发货。
- 每日实发与计划日期冲突时保留两者，不静默覆盖。
- 所有导入、提交、改期、实发、解锁进入操作日志。

## 10. 订舱（本期）与回款（后续）

### 10.1 订舱

- 在导入管理页上传 `订舱申请流程报表`，按 AG 列完整梯号匹配。
- 主状态采用业务简单的两档：`已订舱` / `未订舱`。
- 匹配到 AG，且存在至少一条非 `已作废` 的订舱记录：`已订舱`。
- 没有匹配到 AG，或匹配到的记录全部为 `已作废`：`未订舱`。
- 另设 `订舱审核状态` 列，直接显示 C 列：已完成 / 审批中 / 已作废。
- 匹配到但审批中的行仍显示 `已订舱`，审核状态为 `审批中`，便于区分“没有申请”和“申请尚未审批完成”。
- 同一梯号有多条订舱记录时：有任意 `已完成` 时审核状态取 `已完成`；否则取最新非作废记录；全部作废则显示 `已作废`。
